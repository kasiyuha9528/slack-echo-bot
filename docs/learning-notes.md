## 1. 学習ログ

### ステップ0:作業環境の準備

**やったこと**
- 要件を整理し、プロジェクトフォルダ `slack-echo-bot` を作成した
- README と、このノートの骨組みを作った

**つまずいたこと:ホームフォルダが Git 管理下になっていた**
- `C:\Users\User` の直下に `.git` フォルダがあり、ホームフォルダ全体が Git のリポジトリになっていた
- 中身を調べると、コミットされたのは小さなファイル2つだけで、GitHub に個人ファイルが上がった形跡はなかった
- ただ、`.git` の中に不要なファイルのコピーが大量に溜まっていたので、削除した

**理解したこと**
- Git は、実行した場所から上の階層に向かって `.git` を探し、最初に見つかったものを使う。そのため、プロジェクトの外側に `.git` があると、意図しない範囲を管理してしまうことがある
- `git init` は、**必ずプロジェクトのフォルダの中で**実行する
- `git add .` は「いまのフォルダの全部」を登録するコマンドなので、実行する場所の確認が大切

### ステップ1:Slack App の作成とスコープ設定

**やったこと**
1. api.slack.com/apps でアプリ `parrot-bot` を作成した(テスト用ワークスペース)
2. Bot のスコープに `app_mentions:read` と `chat:write` の2つだけを追加した
3. Bot のイベントに `app_mention` を購読した
4. 「Create and Install」でワークスペースにインストールした
5. テスト用チャンネルに Bot を招待した

**つまずいたこと:Slack の画面が事前の想定と違っていた**
- 想定していた「From scratch」という選択肢はなく、「Blank app」だった。選ぶと、次の画面のタイトルが「Create from scratch」だった
- スコープとイベントの設定が、アプリ作成のウィザード(4ステップ)の中に含まれていた
- 最後のボタンは「Create」ではなく「Create and Install」で、作成とインストールが一度にできた
- 学び:サービスの管理画面は予告なく変わる。手順書より、実際の画面を見て判断する

**理解したこと**
- **スコープ**は、Bot に許可する操作のリスト。必要なものだけにする(最小権限の原則)
- `app_mentions:read` は、自分へのメンションだけを見られる権限。チャンネルの全メッセージを見る権限ではない
- **イベント購読**は、Slack で起きた出来事のうち、Bot に知らせてほしいものを選ぶ設定
- スコープ(できること)とイベント(知らせてもらうこと)は別の設定で、セットで考える
- Basic Information の画面には、秘密の値がいくつかある。**Signing Secret** は今回使う。**Client Secret** と **Verification Token** は使わない
- Verification Token は廃止予定のもの。スクリーンショットに写ってしまったので、念のため再生成した
- Bot トークン(`xoxb-` で始まる)と Signing Secret は、チャットや GitHub に載せない。`.env` ファイルで管理する(次のステップ以降)
- Socket Mode という、公開 URL なしで Slack につなぐ別の方式もある。今回の案件は Webhook(HTTP)で受ける方式なので、使わない

### ステップ2:ローカルで Bolt を起動し、ngrok で疎通確認

**やったこと**
- Node.js のプロジェクトを作り、Bolt(v5.1.0)をインストールした。ESM 形式で書き、秘密の値は `.env` に置いた(Git に載せるのは `.env.example` だけ)
- `node --env-file=.env src/app.js` で、`.env` を読み込んで Bot を起動した
- ngrok(静的ドメイン)で、ローカルの Bot をインターネットに公開した
- Slack の Request URL を登録し、**Verified** を確認した。`app_mention` のイベントが Bot に届き、ログに出た

**つまずいたこと**(原因が分かったものと、分からなかったものを分けて記録する)

| # | 内容 | 原因 | 対処 |
|---|---|---|---|
| 1 | ngrok.exe が消え、起動できなくなった | ウイルスバスターが PUA として検出して削除した(分かった)。ストア版は状態が `Tampered` になった | zip 版を専用フォルダに置き、例外設定を追加。署名(Authenticode)が有効なことを確認した |
| 2 | エラー画面に authtoken が写った | エラー出力に、入力したコマンドがそのまま出るため(分かった) | authtoken を作り直した |
| 3 | Event Subscriptions に「Socket Mode is enabled」と出た | Socket Mode が有効だった(分かった) | Request URL 方式にするため、オフにした |
| 4 | Request URL の確認が失敗し、Bot に `signature mismatch` と出た | **未特定**。`.env` の値を再コピーして保存し、Bot を再起動したら Verified になった。値の取り違えか、再起動漏れの可能性があるが、どちらかは確認できていない | `.env` の値の再コピーと、Bot の再起動 |
| 5 | メンションしても、ngrok にイベントが届かなかった | **未特定**。設定はすべて保存済みだったが、「Reinstall」を押すと届くようになった | アプリの再インストール |
| 6 | Bot Token がスクリーンショットに全文写った | Install App の画面で、トークンが表示されていた(分かった)。再インストールだけでは、トークンは変わらなかった | `auth.revoke` で失効させ、再インストールで再発行して、`.env` を更新。Bot をチャンネルに招待し直した |
| 7 | PowerShell で `.env` の日本語が文字化けし、点検コマンドが空振りした | `Get-Content` の既定の文字コードで読んだため(`-Encoding UTF8` で正しく読めた)。点検コマンドの前提が足りなかった | `-Encoding UTF8` を付けて点検をやり直した |

**理解したこと**
- 経路の確認は、**ngrok の記録(`127.0.0.1:4040`)と、Bot のログの両方**を見ると、切り分けができる。「届いていない」のか、「届いたが拒否した」のかが分かる
- 以前に出た 404 と 401 は、手で送ったテスト(GET と、署名なしの POST)に、Bolt が正しく反応した結果だった。Bolt は、署名のないリクエストを拒否し、そのことをログに出す
- Slack の確認(Verified)は、本物の Slack からの署名つきリクエストを、Bot が受けて応答できるかのテストになる
- 実際のメンションのイベントでは、`text` の先頭に `<@Botのユーザーid>` が付く。返信に使う `ts`(メッセージの時刻 ID)と `channel` も含まれる。画像付きの場合の形は、まだ見ていない(ステップ3で、実際に送って確認する)
- 秘密の値(トークンなど)が、チャットやスクリーンショットに出たら、その場で失効させて作り直す
- 原因が分からなかったことは、「未特定」と記録する。分かったふりをしない

### ステップ3:オウム返しロジックの実装

**やったこと**
- 返信の判断(`reply.js`)、二重処理の防止(`dedupe.js`)、テスト10件を作り、`app.js` から使うようにした
- Bolt のコード(インストール済みのもの)を読んで、`context.botUserId`・`say`・ack のタイミングを確認してから実装した
- 画像・ファイル付きのイベントを、実際に送って `files` の形を確認してから実装した
- Slack で6パターンを確認し、すべて期待どおりだった。返信は3秒以内(体感)

**確認した6パターン**

| # | 送ったもの | 結果 |
|---|---|---|
| ① | 文章だけ | そのまま返信 |
| ② | メンションだけ | 「本文が空っぽ」のお知らせ |
| ③ | 文章 + 画像 | 断りの一言 + 本文 |
| ④ | 画像だけ | 断り + 文字を入れてほしいというお願い |
| ⑤ | `@channel` を含む文章 | 通知が飛ばない文字(`@channel`)に変えて返信 |
| ⑥ | スレッドの中でメンション | 同じスレッドに返信 |

**つまずいたこと**

| # | 内容 | 原因 | 対処 |
|---|---|---|---|
| 1 | `npm pkg set` で `EJSONPARSE` が出た | `package.json` の末尾に、コマンドの文字が入っていた(分かった)。VS Code のファイルに貼ってしまったと思われる(推測) | 末尾の余計な行を消し、ターミナルで実行し直した |
| 2 | `app.js` の末尾2行(`app.start` など)が消えていた | 案内に「この2行は残す」の一言がなかった(分かった) | 2行を戻した。ファイルを読んで、実行の前に気づけた |
| 3 | 貼ってもらったログに、④の行がなかった | 貼り付けの漏れだった(後で確認できた) | ログの「返信の長さ」を、返信の文字数と照らして突き合わせた |

**理解したこと**
- 判断の部分(`reply.js`)を、Slack につながない関数にすると、**Slack なしで10件のテストを確認できる**。Vercel でも使い回せる
- Bolt は、Events API のリクエストを、**リスナーの実行前にすぐ応答(ack)する**。そのため、ローカルでは再送は起きにくい。サーバーレスでは、応答のあとで処理が止まる可能性があるので、ステップ4で確認する
- 二重処理の防止は、メモリ上の記憶なので、1つのプロセスの中だけで効く。実際の再送での動作は、まだ確かめていない
- ログには、本文やファイル名を出さず、必要最小限(チャンネル、ファイル数、返信の長さ)だけにする
- `@channel` などをそのまま返すと、Bot が代わりに全員へ通知してしまう可能性があるため、普通の文字に変えた
- ライブラリの公式の説明だけでは、細かい仕様が分からないことがある。インストール済みのコードを読むと、確実に確認できる

### ステップ4:Vercel 向けに構成を調整してデプロイ

**やったこと**
- Vercel 用の公式ライブラリ `@vercel/slack-bolt` を、インストール済みのコードで確認してから使った(`VercelReceiver`、`createHandler`、`deferInitialization`)
- 返信の処理を `src/handlers.js` に切り出し、ローカル用(`src/app.js`)と Vercel 用(`api/slack/events.js`)の両方から使う形にした
- GitHub の公開リポジトリ `kasiyuha9528/slack-echo-bot` を作り、コミット履歴の全体に秘密の値が含まれていないことを調べてから push した
- Vercel(Hobby プラン)に GitHub のリポジトリを取り込んだ。Application Preset は「Other」、Build などの設定は既定のまま
- 環境変数 `SLACK_BOT_TOKEN` と `SLACK_SIGNING_SECRET` を、Vercel の画面で登録した。**Sensitive(登録後に値を隠す設定)**を使った
- デプロイは成功(12秒)。Deployment Summary の Functions に、`/api/slack/events`(Node.js 24.x)が作られていた

**つまずいたこと**

| # | 内容 | 原因 | 対処 |
|---|---|---|---|
| 1 | デプロイ直後のプレビューが「404 NOT_FOUND」だった | トップページ(`/`)用のファイルが、このプロジェクトにないため(推測。Functions に入口があることは、あとで確認した) | 入口の URL(`/api/slack/events`)側で確認した |
| 2 | ブラウザで入口の URL を開くと「HTTP ERROR 405」が出た | 入口は POST だけを受け付ける作りで、ブラウザで開く操作は GET のため(分かった。Request Logs でも `GET 405` と確認した) | 異常ではないと判断した。404 ではないので、関数が存在することの確認になった |
| 3 | 「Logs」を開いたが、探していたビルドのログではなかった | Vercel の「Logs」(Request Logs)は、アクセスの記録で、ビルドのログとは別だった(分かった) | Deployments → デプロイの詳細 → 「Deploy Logs」を開いた |

**理解したこと**
- Vercel の関数は、常に動いているサーバーではなく、**リクエストが来たときに動く**。そのため、ローカルの `app.start()` のような待ち受けは使わず、`export const POST` で受け口を渡す
- 画面の「Logs」(アクセスの記録)と、デプロイの詳細の「Deploy Logs」(ビルドの記録)は別物。調べたいことで、見る場所が変わる
- HTTP 405 は「その URL はあるが、その方法(メソッド)は受け付けない」という意味。404(その URL がない)と区別すると、関数の存在を確認できる
- ローカルの `.env` と、Vercel の環境変数は、**別々の場所**にある。Vercel 側にも、同じ値を登録しないと動かない
- 環境変数を登録する画面は、値が写りやすい。スクリーンショットを撮らない。Sensitive を使うと、登録後は値が見えなくなる

### ステップ5:本番 URL への切り替えと達成基準の確認

**やったこと**
- Vercel の Request Logs を「Live」にしてから、Slack の Request URL を `https://slack-echo-bot.vercel.app/api/slack/events` に変更した
- Slack で **Verified** になり、Vercel のログに `POST 200 /api/slack/events` が出た。Deployment Protection に、Slack の通信が止められていないことも分かった
- メンションを送ると、返信が **2秒以内**に届いた。Vercel のログにも「メンション受信」が出た
- ステップ3の6パターンを、Vercel 上でも確認した(下の表)

**確認した6パターン(Vercel 上)**

| # | 送ったもの | 結果 |
|---|---|---|
| ① | 文章だけ | そのまま返信 |
| ② | メンションだけ | 「本文が空っぽ」のお知らせ |
| ③ | 文章 + 画像 | 断りの一言 + 本文 |
| ④ | 画像だけ | 断り + 文字を入れてほしいというお願い |
| ⑤ | `@channel` を含む文章 | 通知が飛ばない文字に変えて返信 |
| ⑥ | スレッドの中でメンション | 同じスレッドに返信 |

すべて期待どおりで、二重返信はなかった。

**達成基準の確認**

| 基準 | 結果 |
|---|---|
| Slack で、3秒以内に反応する | 2秒以内(普通の文章で1回確認) |
| ngrok ではなく、ホスティングの URL で動く | Vercel で、6パターンとも確認した |
| Bot トークンを環境変数で管理する | ローカルは `.env`、Vercel は環境変数 |

**まだ確認できていないこと**
- Slack の**再送が起きたときに、二重処理の防止が効くか**。今回は再送が起きていないので、「二重返信がなかった」ことは、防止が効いた証拠にはならない。しかも、防止のメモリは、サーバーレスでは、リクエストをまたいで残らない可能性がある
- **しばらく使わなかったあとの、最初のメンション**(コールドスタート)が、3秒以内に収まるか。計測は1回だけで、これは「通常の状態」の結果

**理解したこと**
- Verified は、「本物の Slack の署名つきの通信が、Vercel 上の Bot に届き、検証を通った」ことの確認になる。ブラウザの GET では、これは確認できない
- Request URL を切り替えると、イベントの届け先が変わる。ローカル(ngrok)の Bot には、届かなくなる
- 「動いた」ことと、「再送や、時間のかかるケースでも動く」ことは別。確認できていないことは、分けて記録する

| `say({ text, thread_ts })` | イベントのチャンネルに投稿する。`thread_ts` を付けると、そのスレッドへの返信になる | オウム返しの返信 |
| `context.botUserId` | Bolt が持っている、Bot 自身のユーザー ID | 本文から Bot 自身のメンションを取り除く |
| `body.event_id` | イベントごとの ID。再送されても、同じ ID になる | 二重処理の防止 |
| `new RegExp(...)` | 文字のパターン(正規表現)を、プログラムの中で組み立てる | `<@Botのid>` を探して取り除く |
| `Set` | 重複しない値の集まり。入れた順を覚えている | 処理済みのイベント ID の記憶 |
| `??` と `?.` | `??` は、左が空(`null` か `undefined`)のときだけ右を使う。`?.` は、途中が空でもエラーにせず `undefined` にする | `event.thread_ts ?? event.ts`、`event.files?.length` |
| `node:test` と `assert.equal` | Node.js 標準のテスト機能。`assert.equal(結果, 期待する値)` で、一致を確かめる | `reply.test.js` と `dedupe.test.js` |
| `npm test` と `npm start` | `package.json` の `scripts` に登録したコマンドを実行する | テストの実行と、Bot の起動 |
| `export const POST` | POST リクエストを受け付ける関数を、外に公開する書き方(Vercel の Web 標準の形式) | `api/slack/events.js` |
| `VercelReceiver` と `createHandler(app, receiver)` | Vercel 用の受け口と、それを Bolt につなぐ関数 | Vercel での Bot の受付 |
| `deferInitialization: true` | Bolt の初期化を、起動時ではなく、リクエストが来たときに遅らせる設定 | リクエストごとに初期化する Vercel の仕組みに合わせた |
| `engines.node` | `package.json` で、使う Node.js のバージョンを指定する項目 | `"24.x"` |

### 用語

| 用語 | 意味 | このプロジェクトでの使いどころ |
|---|---|---|
| Slack App | Slack に機能を追加するプログラムの登録単位 | `parrot-bot` |
| ワークスペース | Slack の利用単位(会社やチームごとの空間) | テスト用ワークスペースで開発する |
| Bot | 人間の代わりに自動で動くユーザー | メンションに返信する役 |
| スコープ(Scope) | アプリに許可する操作の範囲 | `app_mentions:read` と `chat:write` |
| 最小権限の原則 | 必要な権限だけを与えるという考え方 | スコープを2つに絞った |
| イベント購読(Event Subscriptions) | Slack で起きた出来事のうち、通知してほしいものを選ぶ設定 | `app_mention` を購読した |
| `app_mention` | Bot がメンションされたときに発生するイベント | オウム返しのきっかけ |
| Webhook | 出来事が起きたとき、相手のサーバーに自動で送られる連絡(HTTP リクエスト) | Slack から Bot への通知方式 |
| Bot トークン(`xoxb-`) | Bot が Slack に操作を依頼するときの身分証。秘密の値 | `.env` で管理する |
| Signing Secret | Slack からのリクエストが本物か確認するための鍵。秘密の値 | 署名検証に使う(N3) |
| Verification Token | 古い方式の確認用トークン。廃止予定 | 使わない。写ったので再生成した |
| Socket Mode | 公開 URL なしで、Bot から Slack につなぎにいく方式 | 今回は使わない(Webhook 方式が要件) |
| localhost | 「このパソコン自身」を指す名前 | 開発中の Bot の住所。外部から届かない |
| ngrok | 自分の PC に、インターネットから届く一時的な URL を貸すサービス | 開発中に Slack からの通知を受ける |
| Bolt | Slack アプリを作るための公式フレームワーク | Bot の本体 |
